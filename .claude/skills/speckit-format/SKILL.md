## Purpose

`.husky/pre-commit` runs `lint-staged` (eslint --fix + prettier --write), but it only ever sees
files that are **staged at commit time**. Content that lands in the repo any other way — a
`git commit --no-verify`, husky not yet installed in a fresh clone (`npm install`/`prepare` not
run), a squash-merge or cherry-pick that replays a commit without hooks — skips formatting
entirely and only surfaces later, as a `format:check` failure in CI. That is exactly what happened
with `specs/028-klaro-nav-integration/tasks.md`.

This skill closes that gap by running the same formatting **explicitly**, as its own step, right
before `speckit-git-commit` runs — so formatting no longer depends solely on the commit-time hook
firing correctly. It is registered as a **mandatory** hook in `.specify/extensions.yml`, ahead of
each `speckit-git-commit` hook it precedes (lower priority number = runs first), on every phase
that generates spec-kit documents and auto-commits them: `after_specify`, `after_plan`,
`after_tasks`, and `after_implement`. (The original bug was actually in `tasks.md`, generated by
`/speckit-tasks` — not implementation code — which is why this isn't scoped to `after_implement`
alone.)

**Why lint-staged, not `nx format:write`**: `nx format:write` only formats the extensions Nx's
default formatter target covers (js/ts/json/css/html/…) — it silently skips `.md` files in this
workspace, which is exactly the file type that slipped through here. `lint-staged`'s glob in
`package.json` explicitly includes `md`, so it's the correct tool for this job.

## Execution

1. **Confirm formatting tooling is actually wired up** — don't assume the hook install worked:
   - `git config core.hooksPath` should print `.husky/_`. If it's empty, run `npm run prepare`
     (invokes `husky`) to (re-)install hooks, then re-check.
   - This guards the exact failure mode that caused the original bug: a clone/CI checkout where
     `npm install`'s `prepare` script never ran, so hooks were never wired even though
     `lint-staged` is configured.

2. **Stage everything the implementation touched**, so `lint-staged` (which only acts on staged
   files) can see it:

   ```
   git add -A
   ```

   This is safe to run before `speckit-git-commit`'s own `git add .` — it's idempotent, and
   `speckit-git-commit` re-stages after formatting rewrites files anyway.

3. **Run lint-staged directly** (not through a commit, so failures are visible now rather than
   inside the commit hook's output):

   ```
   npx lint-staged
   ```

   This applies `eslint --fix` to code files and `prettier --write` to `ts/tsx/js/jsx/cjs/mjs/
json/html/scss/css/md` per the `lint-staged` config in `package.json`, and re-stages whatever it
   changes.

4. **If `lint-staged` reports files it couldn't auto-fix** (e.g. an ESLint error requiring a manual
   change), stop and fix those before continuing — don't let `speckit-git-commit` commit
   unformatted or lint-failing content. Mirror the "incomplete checklist" pattern used elsewhere in
   this workflow: surface it, don't silently proceed.

5. **If nothing was staged** (implementation made no file changes, or a prior step already
   committed everything), skip silently — nothing to format.

## Done When

- [ ] `core.hooksPath` confirmed set (or repaired via `npm run prepare`)
- [ ] `lint-staged` has run over every uncommitted/untracked file from the implementation
- [ ] Any files `lint-staged` couldn't auto-fix are resolved before `speckit-git-commit` runs
- [ ] Working tree contains only formatted, lint-clean changes by the time the `after_implement`
      `speckit-git-commit` hook runs
