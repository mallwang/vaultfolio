## Prior Art

- **Internal role model already exists but is coarse.** [specs/005-auth-sessions-isolation/spec.md](specs/005-auth-sessions-isolation/spec.md) (FR-011) establishes exactly two roles server-side — Administrator and a regular member — enforced per-request, with no notion of finer-grained "scopes" or per-feature entitlements. Today's role system is binary, not a scoping/entitlement system a microfrontend-gating mechanism could hang off directly. — [source: specs/005-auth-sessions-isolation/spec.md] (confidence: high)
- **No billing/subscription system exists anywhere in the codebase.** No billing entities, payment integration, or subscription-tier concept appears in `libs/domain`, `apps/backend`, or any spec 001–019. Billing-based gating is entirely speculative today. — [source: repo search, `specs/` directory listing 001–019, `libs/domain`] (confidence: high)
- **An existing architectural seam for feature gating already exists**: [specs/009-app-shell-restructure/spec.md](specs/009-app-shell-restructure/spec.md) established a single app shell with a side-nav that is already conditionally rendered based on authentication state, and the shell routes authenticated pages under `/app`. This is the natural integration point a microfrontend loader would plug into — the app doesn't need a new "composition surface," it already has one (just not federation-based). — [source: specs/009-app-shell-restructure/spec.md] (confidence: high)
- **Toolchain has a supported path to Module Federation without adding new tooling**: `@nx/angular` 23.1.1 is already a devDependency, and Nx's `@nx/angular` package ships `host`/`remote` generators for build-time Module Federation setup on Angular + Webpack (the workspace already uses `@nx/webpack` per `nx.json` plugins). Adopting the clarified approach (Module Federation) would not require introducing an unfamiliar toolchain — it reuses what's already installed. — [source: nx.json plugins list, package.json devDependencies] (confidence: high); the specific claim that `@nx/angular` ships MF generators compatible with Angular ~22 is ASSUMPTION from general Nx/Angular ecosystem knowledge, not verified against installed generator schemas in this repo (confidence: low)
- **No prior internal attempt at this.** Nothing in `specs/001` through `specs/019` (the full history of shipped/drafted features) touches multi-app composition, remotes/hosts, or federation — this would be a first for the project. — [source: specs/ directory listing] (confidence: high)
- **Industry track record is mixed.** Micro-frontend architectures (module federation, single-spa, iframes) are a well-documented pattern for large organizations with multiple independent teams shipping to one shell, but are also widely reported (in general frontend-architecture discourse) as adding real operational cost — versioning/shared-dependency drift, cross-remote testing complexity, bundle duplication risk, and harder end-to-end debugging — costs that are usually justified only once team-scaling pain exists. — ASSUMPTION (general industry knowledge, not fetched from a specific source this session) (confidence: medium)

## Market & Context

- **Deployment shape argues against urgency.** [docker/frontend.Dockerfile](docker/frontend.Dockerfile) and [docker/frontend.nginx.conf](docker/frontend.nginx.conf) show Vaultfolio ships as a single static Angular build served by one nginx container behind a reverse proxy to the backend — the nginx config's own comment references being "deployed on a NAS," i.e., this is a small, self-hosted, single-instance deployment target, not a multi-region or multi-tenant SaaS. — [source: docker/frontend.Dockerfile, docker/frontend.nginx.conf] (confidence: high)
- **The alternative users/maintainers cope with today** is simply: add new features as new routes/modules inside the existing single Angular app (the pattern used by all 19 shipped specs to date). This has worked without friction so far per the "no current pain points" clarification. — [source: intake.md clarifications; specs/001–019 all ship as in-app modules] (confidence: high)
- **Cost of doing nothing**: none identified beyond forgoing the _option_ of independent deploy pipelines per feature — there is no current blocker to shipping new features the conventional (in-repo module) way. — ASSUMPTION (confidence: medium)

## Evidence Against the Idea

- **The idea's own clarifications undercut its urgency**: no current pain point, single team owns everything, and the billing dimension that's part of the pitch ("integrated... based on... billing data") doesn't exist as a system yet — two of the three stated gating dimensions (scope, billing) are either underdeveloped (scope ≈ binary role only) or entirely absent (billing) today. — [source: intake.md] (confidence: high)
- **Scale doesn't match the pattern's usual justification.** Micro-frontend/module-federation architectures earn their complexity primarily when multiple independent teams need independent deploy cadences; a single team shipping ~2-3 features/year with no deploy-cadence conflict is the profile the industry generally associates with _not_ needing this pattern yet. — ASSUMPTION (confidence: medium)
- **Deployment model adds friction, not just build config.** Today's single static-build → single nginx container pipeline ([docker/frontend.Dockerfile](docker/frontend.Dockerfile)) would need real rework to host independently-deployed remotes (versioned remote endpoints, cache-busting, CORS/CSP for cross-origin remotes or a shared origin strategy) — a self-hosted NAS-style deployment is exactly the context where operating multiple independently-versioned remotes is hardest to justify. — [source: docker/frontend.nginx.conf comment about NAS deployment] (confidence: medium)
- **No demand signal exists.** This is a purely anticipatory/speculative idea with no user, ticket, or incident driving it. — [source: intake.md] (confidence: high)

## Update — Scope Clarified as a Product Pivot, Not Just a Frontend Refactor

After this research was first written, the user clarified the actual driver: Vaultfolio is meant to grow from a single investment-tracking app into a multi-domain personal finance app with ~6 planned domains (retirement, insurances, household/budget planner, historic wealth development, account overview, and holdings-as-just-one-domain — see `intake.md` for the full list). This changes several conclusions above:

- **"No concrete feature planned" is now resolved** — there is a concrete, fairly detailed list of planned domains. The earlier gap ("which feature will be the first microfrontend?") is replaced by a new one: whether all six ship as separate microfrontends together or incrementally (see Gaps below).
- **Scale is larger than first estimated.** The original "~2-3 microfrontends" estimate is superseded by a ~6-domain target. This still describes a single-team, low-deploy-conflict effort (per the unchanged "single team" and "no current pain points" clarifications), so the core evidence-against finding — that the industry justification for micro-frontends (independent teams, independent deploy cadences) is not yet present — still holds, arguably more so at this stage, since one team scoping six domains has no cross-team deploy-cadence conflict to resolve.
- **Cross-domain data coupling is a new, unaddressed risk.** Several of the named domains are not independent by nature: "historic wealth development" and "account overview" almost certainly need to aggregate holdings, banking, and possibly insurance data to produce a combined net-worth/cash-flow view. Micro-frontend architectures (especially Module Federation, which composes independently-deployed UI bundles) address _UI/deployment_ independence, not _data_ independence — if the domains share a data model and need cross-domain aggregate views, the hard problem here is a data/API design problem, not a frontend-composition problem, and Module Federation does not solve it. This is a new, high-relevance gap (see below).
- **Billing's applicability is still unresolved and now more consequential.** The domain list (retirement, insurance planning, budget planning) reads like features that could plausibly be tiered/paywalled in a hosted product — but Vaultfolio's current deployment model is self-hosted/NAS-style (single instance, single household), where "billing data" gating has no natural referent. Whether a hosted/multi-tenant offering is _also_ being considered is now a materially important open question, since it changes both the billing-gating rationale and the case for independent deploy pipelines.
