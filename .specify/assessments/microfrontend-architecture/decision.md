## Verdict & Rationale

**Go, with Option B** (Nx domain libraries with enforced boundaries + scoped entitlements) as the recommended approach for `/speckit-specify` to build on — not Module Federation (Option C), the originally proposed technical approach.

The scorecard clears the bar for `go`: problem validity and evidence strength are both `adequate`+ (neither is `weak` or `unknown`), and a recommended concept option exists with a documented alternatives analysis. The research and concept artifacts converge on the same conclusion from different angles — research finds the two conditions that usually justify Module Federation (independent teams, independent deploy cadences) are both explicitly absent and are stated non-goals, and the self-hosted NAS deployment model makes operating independently-versioned remotes unusually costly to justify; concept.md's Option A vs. B vs. C trade-off table reaches the identical conclusion, additionally showing that Option A (do nothing structurally beyond a route guard) under-delivers on the actual coupling goal because nothing enforces the boundary, only convention does. Option B is the one option that satisfies both of the problem statement's stated goals (bounded coupling; centralized, extensible gating) without adopting operational machinery (runtime remote composition, independently deployed bundles) the evidence says isn't needed at this team size and deployment shape — while leaving that door open later, since the entitlements seam and enforced boundaries it establishes make a future move toward Option C smaller, not wasted work, should a hosted/multi-tenant/multi-team future actually materialize.

The one `unknown`-adjacent gap — whether the six domains share enough underlying data (e.g., a combined net-worth view) to need cross-domain aggregation — is explicitly and knowingly carried forward rather than glossed: concept.md scopes it out as "a separate data-architecture problem, not addressed here," and problem.md's non-goals do the same. This is acceptable for a `go` because it doesn't block _this_ decision (which domain library/boundary structure to adopt) — it does need to be picked up explicitly when the first domain that requires cross-domain data (e.g., "account overview" or "historic wealth development") reaches specification, so it is carried forward below rather than silently dropped.

## If go — Handoff to `/speckit-specify`

- **Problem**: Vaultfolio is pivoting from a single investment-tracking app to a six-domain personal finance app (holdings, retirement, insurances, household/budget planning, historic wealth development, account overview), and today's single undifferentiated Angular app has no structure to add, gate, and maintain multiple domains without them tangling as the count grows.
- **Chosen approach**: Option B — scaffold each domain as its own Nx library group (`libs/frontend/<domain>/feature|data-access|ui`) with `domain:*` boundary tags enforced via `@nx/enforce-module-boundaries` (extending the workspace's existing `scope:*` tag convention), plus one shared `libs/frontend/entitlements` lib exposing `canAccessDomain(user, domain)` — backed by extending the existing binary role (spec 005) with a `scopes: DomainKey[]`-style field — consumed identically by route guards and by the spec-009 app-shell's nav filtering. Same single `apps/frontend` build and NAS/nginx deploy throughout; no runtime remote composition. Holdings is re-homed into the same library shape first, proving the pattern before the other five domains follow it.
- **In scope / out of scope**:
  - In scope: the domain-library + boundary-tag + entitlements-lib structure itself; the lint enforcement mechanism; extending the role model with a scope field; retrofitting holdings into the new shape (boundary + entitlement check only, not an internals rewrite).
  - Out of scope: independent deploy cadences or independently-versioned/deployed domain bundles (Module Federation); any billing/subscription system or billing-based gating; cross-domain data aggregation/API design (e.g., a combined net-worth view spanning holdings + banking + insurance data); deciding which of the five new domains ships first or whether they ship together vs. incrementally (a roadmap/sequencing decision for specification).
- **Success metrics**:
  - A new domain can be added without requiring changes to unrelated existing domains' code, tests, or deploy path (enforced by lint, not just convention).
  - Whether a user can see/use a given domain is controlled per-user via the shared entitlements function, not domain-specific conditionals scattered through the app.
  - The single team's per-domain build/maintenance effort does not grow superlinearly as domains are added (no established baseline yet — first data point comes from the holdings retrofit + first new domain).
- **Carried-forward open questions**:
  - Do the six domains ship all at once or incrementally, and if incremental, which new domain ships first? (explicitly deferred to specification/roadmap, not architecture)
  - Do any domains (notably "account overview" and "historic wealth development") require cross-domain data aggregation, and if so, how is that data/API design handled given each domain's `data-access` lib is boundary-isolated from the others? (explicitly out of scope for this architecture decision; needs to be addressed before/alongside specifying whichever domain first needs a cross-domain view)
  - Confirm `@nx/enforce-module-boundaries`'s `depConstraints` can express the proposed per-domain `onlyDependOnLibsWithTags` scheme cleanly against this workspace's actual project structure (concept.md "Assumptions to Validate" — not verified this session).
  - Confirm extending the existing binary Administrator/member role (spec 005) with a `scopes` field is an acceptable incremental change to the auth/session model, rather than needing a broader auth redesign (concept.md "Assumptions to Validate").
