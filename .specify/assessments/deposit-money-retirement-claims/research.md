## Prior Art

- **Internal precedent — 017-restructure-asset-types** (`specs/017-restructure-asset-types/spec.md`, merged as PR #28, `e664e55`): the project already went through an asset-type generalization cycle — renaming `GOLD`→`PRECIOUS_METAL` and `BITCOIN`→`CRYPTO` and adding a required free-text `name` field so a single asset type can represent a family of related instruments (Gold/Silver/Platinum; Bitcoin/Ethereum) instead of one hardcoded value. This is directly analogous to how "deposit money" would need to represent multiple cash locations (bank, cash-at-home, broker reference account) under one type. — [source: specs/017-restructure-asset-types/spec.md] (confidence: high, cited)
- **Internal precedent — the `Management` field** (`specs/003-manual-holdings-entry/spec.md` lines 18–291): every holding, regardless of asset type, already carries a required free-text `Management` field identifying "who holds/manages" it (e.g. "Private", "Roboadvisor", a bank name). This field already covers the "which bank account / which former employer / which insurer" dimension the intake note describes for both new types — it may mean neither new type needs a bespoke "provider" field of its own. — [source: specs/003-manual-holdings-entry/spec.md] (confidence: high, cited)
- **Internal precedent — manual-valuation asset types**: `PRECIOUS_METAL` already models a manually-priced, non-market-quoted asset (`weightGrams` required, `currentValue` optional, no live price feed) — [source: libs/domain/holdings/src/lib/asset-type.ts]. This is the closest existing shape to what "deposit money" (a balance, not a priced position) and "retirement claims" (a claim, not a priced position) would need: a name + a manually-entered value, no ISIN, no market pricing. (confidence: high, cited)
- **No external prior art gathered.** Comparable products (e.g. Empower/Personal Capital, YNAB, Kubera) commonly separate "liquid net worth" from "future/illiquid" assets, but this claim is not sourced from a fetched page in this research pass — no URL was supplied and none of the allowlisted hosts were relevant, so nothing was fetched per the URL Trust Policy. — ASSUMPTION (confidence: low; flagged for follow-up if external validation is wanted)

## Data & Constraints

- **No live pricing/market-data dependency for either type.** The codebase has zero implemented price-feed integration (`libs/market-data` is reserved and empty, `TODO(MARKET_DATA_PROVIDER)` in the constitution) and the README states the app "does not connect to any bank or brokerage APIs — all data is entered manually." Both proposed types are naturally manual-entry (a balance figure; a claim's current/projected value), so they introduce no new integration surface. — [source: README.md; .specify/memory/constitution.md; libs/market-data] (confidence: high, cited)
- **No net-worth/total-wealth aggregation feature exists yet to decide the "include or exclude" question against.** `apps/frontend/src/app/dashboard/dashboard.component.ts` currently renders "total value" and "today's change" as explicit placeholders, not real aggregation. — [source: apps/frontend/src/app/dashboard/dashboard.component.ts:11,31] (confidence: high, cited). This means the requester's stated uncertainty ("should retirement claims count toward the same wealth view?") is not yet a live conflict in the running product — it becomes one only once a real total-wealth aggregate is built, which is a separate, not-yet-built feature.
- **Library-First and API-First constitution principles** (`.specify/memory/constitution.md` Principles I–II) would require any new asset-type logic (field validation, merge/lot behavior) to live in `libs/domain/holdings` and be exposed via `libs/api-contract`, consistent with how `PRECIOUS_METAL`/`CRYPTO`/`ETF`/`SHARE` are structured today — a straightforward, well-precedented extension rather than a new architectural pattern. — [source: .specify/memory/constitution.md] (confidence: high, cited)
- **Migration precedent exists and is idempotent-safe**: 017-restructure-asset-types shipped a one-time data migration pattern (FR-007/FR-008) for evolving the asset-type enum without data loss — the same pattern would apply to adding wholly new enum values (which is additive and simpler than the rename it already handled). — [source: specs/017-restructure-asset-types/spec.md FR-007/FR-008] (confidence: high, cited)

## Evidence Against the Idea

- **Scope/complexity risk for "retirement claims" specifically**: unlike every existing asset type, a retirement claim has no clear "current value" in the same sense as a market position — its value may be a projected future payout, an accrual-to-date figure, or entirely unknown until closer to retirement. Forcing it into the existing `Holding` shape (name + value fields) risks either (a) a misleadingly precise-looking number sitting in a net-worth total, or (b) a special-cased field set that doesn't fit the codebase's current "manually-entered current value" pattern as cleanly as `PRECIOUS_METAL` does. This is the requester's own stated hesitation and is corroborated by the fact that no total-wealth feature exists yet to even define what "counting toward wealth" would mean. — [source: intake.md; apps/frontend/src/app/dashboard/dashboard.component.ts] (confidence: medium, cited)
- **No accessible/liquid vs. illiquid distinction exists anywhere in the current data model** (`libs/domain/holdings/src/lib/asset-type.ts` has no such flag on any type). Adding "retirement claims" without first deciding whether/how illiquidity should be represented risks a half-modeled feature that later needs rework once a real net-worth or liquidity view is built. — [source: libs/domain/holdings/src/lib/asset-type.ts] (confidence: medium, cited)
- **"Deposit money" risks conflating several distinct real-world things** (bank balance, physical cash, broker reference-account cash) under one type/name field, the same way `PRECIOUS_METAL` conflates Gold/Silver/Platinum today — that precedent worked because those are genuinely fungible-in-kind holdings; whether checking-account cash, home cash, and broker cash are similarly interchangeable for the requester's purposes (e.g. for filtering/reporting) is untested. — ASSUMPTION (confidence: low; worth confirming in `/speckit-assess-define`)
- **No counter-evidence found that this shouldn't be built at all** — both types are well within the product's stated purpose ("tracks what you've invested... not day-to-day spending" arguably already stretches to include bank deposits since they're capital, not spending) and fit the existing manual-entry model. The strongest objection is sequencing/design uncertainty (above), not desirability.
