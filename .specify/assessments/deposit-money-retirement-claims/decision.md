## Verdict & Rationale

**Go.** Problem validity, evidence strength, value vs. inaction, feasibility, and strategic fit all score `strong`, and concept.md has a recommended, appetite-bounded option (Option A: two new manual-value asset types on the `PRECIOUS_METAL` pattern). Risk posture is `adequate` rather than `strong` because the retirement-claim valuation nuance (current vs. projected value, vesting date) is real and still open — but concept.md handles this correctly by scoping it out of the recommended option rather than pretending it's solved, and problem.md carries it forward as an explicit open question for specification to resolve. That is a properly managed risk, not an unmitigated one, so it does not block a `go`.

## If go — Handoff to `/speckit-specify`

- **Problem**: Vaultfolio has no asset type for fiat cash balances (bank/home/broker reference-account cash) or accrued retirement entitlements (employer pension, Riester-Rente, insurance-based retirement), so tracked holdings understate the user's actual personal wealth or get mislabeled under an unrelated type as a workaround.
- **Chosen approach**: Concept Option A — add `DEPOSIT_MONEY` and `RETIREMENT_CLAIM` to the `AssetType` union, each requiring a free-text `name` and manually-entered `currentValue`, reusing the existing `Management` field for provider identity — following the same shape and migration pattern already established by `PRECIOUS_METAL`.
- **In scope**: New asset-type enum values, their field requirements (`name` + `currentValue`, no ISIN/quantity/price feed), holdings-entry UI and validation for both types, one-time data migration consistent with the 017-restructure-asset-types precedent.
- **Out of scope**: Total-wealth/net-worth aggregation (feature doesn't exist yet); liquid vs. illiquid flagging or filtering; projected-value/accrual modeling, vesting or access dates for retirement claims; live price feeds or bank/brokerage API integration; a dedicated sub-classification field for deposit-money location beyond `name` + `Management`.
- **Success metrics**: User can enter a deposit-money holding and a retirement-claim holding through Vaultfolio's normal holdings-entry flow (baseline: not possible today); tracked holdings no longer omit or mislabel cash/retirement entitlements (baseline: currently omitted or miscategorized).
- **Carried-forward open questions**:
  - Should retirement claims be included in total net worth once a real total-wealth aggregate exists, shown separately/flagged as illiquid, or both — no such aggregate exists yet to anchor this decision.
  - Should a retirement-claim holding record current accrued value, projected value, or both; is a vesting/access date required?
  - Does "deposit money" need sub-classification beyond free-text `name` + `Management`, e.g. for filtering/reporting?
  - Does the existing `Management` field sufficiently capture "which employer/insurer/bank" for both new types, or is a dedicated field needed?
  - Multi-currency handling for deposit money — assume EUR, or reuse an existing currency concept if one exists?
