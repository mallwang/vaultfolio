# Quickstart: validating Parser Requests

Runnable scenarios that prove the feature end to end. Details of shapes live in
[contracts/](contracts/) and [data-model.md](data-model.md). Use `npm`/`npx` (project convention);
test credentials come from the dedicated test user, never from `.env`.

## Prerequisites

- `npm ci`; backend + frontend runnable (`npm run dev` → `nx run-many -t serve -p backend frontend`).
- A user with the **Earnings** domain entitlement, and an administrator account.
- SMTP pointed at a local catcher (e.g. MailHog) or the `MailerService` stubbed; `APP_BASE_URL` set
  to an absolute `http(s)` URL.
- Synthetic input PDFs only (generated by the test helper in
  `libs/frontend/domain/earnings/src/testing/`; never a real payslip).

## 1. Automated checks

```bash
npx nx run-many -t lint typecheck test -p requests earnings api-contract notifications \
  frontend-domain-earnings frontend-admin backend
npx nx test backend --testPathPattern=requests.e2e
npx nx run-many -t test --coverage --outputStyle=static -p earnings requests
```

Expected: all green; coverage of `parser-request/` and `libs/requests` at the project's threshold.
The OpenAPI drift check (CI) must pass after regenerating `api/openapi.yml`.

## 2. User flow (US1, US4) — drive with Playwright (`verify-ui` skill)

1. Log in as the entitled test user → Earnings → Import → drop a synthetic **text** PDF in an
   unsupported layout containing planted personal data (IBAN, tax ID, SSN, e-mail, phone, `80331 München`,
   one planted block under a black rectangle).
2. Expect the row "format not supported yet" with **Request a parser**; a failed-check row, a
   scan row and a password row show **no** button.
3. Open the wizard: step 1 shows the three-column explanation and the document checks listing
   personal-data _kinds_ (never values); **Continue** is disabled until the consent box is ticked.
4. Step 2: planted values are locked grey blocks; unknown words amber; the covered block is
   preselected "mask"; **Continue** disabled until every marked word is decided.
5. Step 3 (optional): mark _Brutto_/_Lohnsteuer_/_Netto_ lines; live check turns green for a
   consistent synthetic payslip and shows the failing check + involved figure for a wrong marking.
   **Skip markings** also works.
6. Step 4: summary + **Send request**. Capture network traffic: exactly one `POST /requests`, JSON,
   no PDF bytes, and **none** of the planted strings or original amounts appear in the body.
7. Sent screen shows the confirmation; the DB has one `requests` row (OPEN) with a
   `request_attachments` row.

## 3. Admin flow (US2, US3)

1. Admin receives one e-mail per admin in their language: link `…/app/admin/requests?id=<id>`,
   **no attachment**, no sample content.
2. Open the link → Requests tab with the detail displayed; table shows feature, type, requester,
   date, status; the open-count badge matches.
3. **Download PDF** → file `request-xxxxxxxx-sample.pdf` saved (not shown inline); headers:
   `Content-Disposition: attachment`, `nosniff`; one `request_download_audit` row.
4. Open the PDF: same layout as the preview, random values, locked placeholders, no clickable
   content (`pdfdetach`/`qpdf --check` show no attachments/actions).
5. Set status **Done** + note → requester gets the "import again" mail once; setting Done again
   sends nothing.

## 4. Access control (SC-006)

```bash
# as member (Earnings): submit ok, everything else 403
curl -b member.cookie -X POST …/requests -H 'content-type: application/json' -d @valid.json   # 201
curl -b member.cookie …/requests            # 403
curl -b member.cookie …/requests/<id>       # 403 (same body for unknown id)
curl -b member.cookie …/requests/<id>/attachment   # 403
curl …/requests                             # 401
```

## 5. Server-side defence (SC-004, FR-017)

Send, bypassing the browser: a body with an extra key, a 4th page, a 61-char word, a binary
content type, and a body containing a valid IBAN/e-mail → expect `LAYOUT_UNKNOWN_FIELD`,
`LIMIT_EXCEEDED`, `LIMIT_EXCEEDED`, `415`, `PERSONAL_DATA_DETECTED` respectively, nothing stored.
Submit 4 requests as one user → 4th gives `429 REQUEST_LIMIT_OPEN`.

## 6. Retention and purge (US5, SC-009)

Backend spec with the injected clock: Done at T → at T+29 d sample present; at T+30 d the sweep
deletes attachment and payload, row remains (`sample_deleted: true` in detail, download → 410);
reopen at T+10 d → `closed_at` null, nothing deleted later; Open/In-progress samples never deleted;
deleting the requester's account removes their requests, attachments and audit rows.

## 7. i18n / theme / phone (SC-011)

Repeat steps 2–3 in German and English, light and dark, at 390 px width: no untranslated keys
(the translation completeness spec covers `requests.{en,de}.ts`), the two-column splits stack, the
table scrolls inside its container.
